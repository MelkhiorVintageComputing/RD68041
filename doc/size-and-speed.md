# Making it smaller, and making it faster

Each row is a before-and-after on the same tree with one change, from `make impl`
(Artix-7) and `make quartus` (Cyclone V).

| change | kept | what it was worth |
|---|:--:|---|
| **M4 frequency spike** (`make spike`, `sim/spike/rd68041_spike.sv`): the design's ATCs, cache arrays, register file, address adder, shifter and bus unit in the pipeline's arrangement, with stand-in control | measurement | Artix-7 xc7a100t-1, out of context, 33.333 ns constraint: **4,357 LUTs** (600 as memory), 2,176 FFs, 18 RAMB tiles, **21.17 ns, 47.23 MHz**. Limited by OF, the data ATC through the tag compare and way select into the aligner (19 levels); then EX's branch into the instruction cache's RAM address (19.47 ns), IF2 (18.87 ns), EX's ALU (14.61 ns), EA into the data cache's RAM address (13.62 ns) |
| the block RAM written a byte lane per process | no | Vivado could not infer a RAM ("multiple writes via different ports in same process") and built all eight cache ways from registers: 32 minutes in timing optimisation and over 5 GB before the host ran out. One process per port, lanes written out, fixed it (`rtl/rd68041_bram.sv`) |
| the decoder's addressing modes worked out once, outside the decode case (`ea_of`, `DEC_EA`/`DEC_IND`/`DEC_SRC`), instead of about 69 inlined calls in it | yes | yosys on `rd68041_decode` alone: **20 m 47 s and 3.9 GB → 57 s and 450 MB** (19,008 cells). `proc_mux` had taken 93 % of the time on one process of 24,283 signals; it had made `make check` take 86 minutes |
| **M9: the whole processor, caches in** (`make impl`, `c701b41`) | measurement | Artix-7 xc7a100t-1, 33.333 ns constraint: routed slack +1.807 ns, **31.53 ns, 31.72 MHz**; 19,740 LUTs, 996 LUTRAM, 4,949 FFs, 591 CARRY, 10 DSP, 16 BRAM; 5 minutes, 2.4 GB. Limited by instruction fetch: the queue's head into a queue entry's enable (25 levels) -- the cache hit's up-to-four words placed at the tail |
| **M10: the MMU in** (`make impl`, `3d6fd5d`) | measurement | Artix-7 xc7a100t-1, 33.333 ns constraint: routed slack +2.023 ns, **31.31 ns, 31.94 MHz**; 23,600 LUTs, 2,040 LUTRAM, 6,661 FFs, 646 CARRY, 10 DSP, 16 BRAM -- the two ATCs (LUT RAM), the walker and the write-fault frame's capture add about 3,900 LUTs and 1,700 FFs to M9. Limited by the data memory unit's state into an instruction-queue entry's enable (33 levels): whether the write queue is empty holds write-back, and so what the queue takes. The ATC in front of the fast read's tag compare is not the limit |
| **M11: the FPU in** (`make impl`, `b78c356`) | measurement | Artix-7 xc7a100t-1, 33.333 ns constraint: routed slack -0.838 ns, **34.17 ns, 29.26 MHz** -- timing not met; 34,080 LUTs, 2,040 LUTRAM, 9,484 FFs, 1,067 CARRY, 14 DSP, 16 BRAM: the FPU adds about 10,500 LUTs and 2,800 FFs to M10. Limited by EX's register select through the operand selection and the FPU's unpacking into the data path's first step, an add's alignment (35 levels) |
| the FPU data path's inputs registered on start (`rd68041_fpu_dp`, one clock more an FP operation, `doc/timing-divergences.md`) | yes | routed slack +0.408 ns, **32.92 ns, 30.37 MHz**; 33,831 LUTs, 9,658 FFs. The FPU is off the critical path, which is instruction fetch's again: the queue's head into an entry's enable (33 levels) |
| **M12: the MC68LC040** (`make impl FPU=0`, `4a957f8`) | measurement | Artix-7 xc7a100t-1, 33.333 ns constraint: routed slack +1.032 ns, **32.30 ns, 30.96 MHz**; 23,887 LUTs, 2,040 LUTRAM, 6,711 FFs, 646 CARRY, 10 DSP, 16 BRAM -- M10's processor and about 290 LUTs and 50 FFs more: the FP instructions' decode and the format $4 frame, no FPU. Limited by the data memory unit's state into an instruction-queue entry's enable (33 levels) |
| **M12: the MC68040 again** (`make impl`, `4a957f8`) | measurement | routed slack +0.054 ns, **33.28 ns, 30.05 MHz**; 34,303 LUTs, 9,667 FFs, 1,061 CARRY, 14 DSP, 16 BRAM. The same path as M11's, the queue's head into an entry's enable (35 levels), which M12 did not change: placement's spread, 0.3 MHz |
| **M13: the MC68040** (`make impl`, the M13 commit) | measurement | routed slack +1.967 ns, **31.37 ns, 31.88 MHz**; 33,998 LUTs, 2,040 LUTRAM, 9,666 FFs, 950 CARRY, 14 DSP, 16 BRAM. The fixes rd-virt led to: the read-after-write tests on the page offset (12 bits, not 30: fewer LUTs and CARRY), a micro-operation's own An update into EX's operands. The same path as M11's, a register into an instruction-queue entry's enable (35 levels) |
| **M13: the MC68LC040** (`make impl FPU=0`, the M13 commit) | measurement | routed slack +1.644 ns, **31.69 ns, 31.56 MHz**; 23,840 LUTs, 6,709 FFs, 535 CARRY, 10 DSP, 16 BRAM. The data memory unit's state into a queue entry's enable (33 levels), as at M12 |
| **M14: the MC68040** (`make impl`, the M14 commit) | measurement | routed slack +0.481 ns, **32.85 ns, 30.44 MHz**; 33,896 LUTs, 2,040 LUTRAM, 9,664 FFs, 956 CARRY, 14 DSP, 16 BRAM. The one RTL change is a cache-inhibited read held until nothing older is in EX or W (`of_oldest`, `ld_ser_wait`). It is not on the limiting path: EX's valid bit through the FPU's exception check (`x_xv`) and the exception unit into an instruction-queue entry's enable (30 levels), M11's path in another form. 1.4 MHz down, placement's spread as at M12; still 22 % over 25 MHz |
| **M14: the MC68LC040** (`make impl FPU=0`, the M14 commit) | measurement | routed slack +0.636 ns, **32.70 ns, 30.58 MHz**; 23,889 LUTs, 6,707 FFs, 541 CARRY, 10 DSP, 16 BRAM. The data memory unit's state into the fetch address's enable (32 levels), M12's and M13's path, 1.0 MHz slower |
| **M14: the MC68040, the fetch stopped at an ATC fault** (`make impl`, `xstop` in `rd68041_ifu`) | measurement | routed slack +0.660 ns, **32.67 ns, 30.61 MHz**; 33,910 LUTs, 2,040 LUTRAM, 9,666 FFs, 956 CARRY, 14 DSP, 16 BRAM. The change adds a flip-flop and a term to the fetch's lookup request. Limited by EX's second write register into W's CCR (34 levels), not by the fetch. Placement's spread: 0.2 MHz up |
| **M14: the MC68LC040, the same** (`make impl FPU=0`) | measurement | routed slack +1.959 ns, **31.37 ns, 31.87 MHz**; 24,155 LUTs, 6,706 FFs, 541 CARRY, 10 DSP, 16 BRAM. Still the data memory unit's state into an instruction-queue entry's enable (31 levels), M12's path; 1.3 MHz up, which is placement, not the change |
| **M14: the MC68040, a fetch fault taken part-fetched** (`make impl`, `de_qmask` in `rd68041_core`) | measurement | routed slack +0.818 ns, **32.52 ns, 30.76 MHz**; 33,786 LUTs, 2,040 LUTRAM, 9,671 FFs, 959 CARRY, 14 DSP, 16 BRAM. Decode's fault test masked by the words in the queue, and the issue made on it. Limited by the instruction queue's head into a queue entry (34 levels), the path the issue term joins; 0.15 MHz up all the same |
| **M14: the MC68LC040, the same** (`make impl FPU=0`) | measurement | routed slack +2.246 ns, **31.09 ns, 32.17 MHz**; 24,052 LUTs, 2,040 LUTRAM, 6,712 FFs, 544 CARRY, 10 DSP, 16 BRAM. The data memory unit's state into an instruction-queue entry's enable (31 levels), M12's path; 0.3 MHz up |

*Started fresh at M0. The first row is M4's frequency spike.*
